# Delivery Roadmap

This platform's full specification spans 25 deliverables across governance, contract administration (NEC4/SBCC), reporting, document management, audit, Power BI, security, testing, and DevOps. Building all of it as production-grade code in a single pass is not realistic — it is a multi-month, multi-workstream programme. This roadmap sequences delivery so every phase lands a **working, testable increment** rather than a paper design.

## Phase 8 — Document Storage: SharePoint → Azure Blob Storage

- [x] **Replaced the SharePoint-backed active tier with Azure Blob Storage.** `ISharePointDocumentStore` / `GraphSharePointDocumentStore` (Microsoft.Graph, app-only auth via `ClientSecretCredential`) are gone. Reason: Graph's application-permission consent (`Sites.ReadWrite.All` or a site-scoped equivalent) has to be granted by a tenant admin, and that consent is not obtainable in this deployment — see GitHub issue #2. A storage account connection string needs no tenant admin, so it replaced SharePoint entirely rather than sitting unresolved.
- [x] New `IDocumentStore` / `AzureBlobDocumentStore` (renamed from `ISharePointDocumentStore`) is the active tier now; `IBlobArchiveStore` / `AzureBlobArchiveStore` remains the archive tier. Both live in the same storage account (`BlobStorage` config section: one `ConnectionString`, `ActiveContainerName` + `ArchiveContainerName`), which also meant the archive copy could switch from an anonymous `HttpClient` GET against a (would-be-private) SharePoint/Blob URL to an authenticated blob-to-blob copy through the SDK — a real correctness fix, not just a rename, since the old HTTP-GET approach would have 403'd against a non-public active-tier container.
- [x] `DocumentFile.SharePointUrl` renamed to `StorageUrl` end-to-end (entity, EF configuration + migration, DTOs, query handlers, frontend `types.ts`) rather than keeping a misleading name.
- [x] Removed the now-unused `Microsoft.Graph` and `Azure.Identity` package references from `SCPM.Infrastructure`.
- [x] `dotnet build`/unit tests/integration tests re-verified green after the swap; see commit history for the exact migration.
- [x] **Exercised against a real Azure Storage account** (closing GitHub issue #2). The user provided a scoped, short-lived SAS token; a throwaway verification script (not committed, deleted after use) ran the exact upload/overwrite-rejection/archive-copy logic from `AzureBlobDocumentStore`/`AzureBlobArchiveStore` against it. Confirmed against the real service: both containers create correctly, upload succeeds, a second upload to the same path is genuinely rejected with `409 Conflict` (the "never overwrite" guarantee holds, not just in theory), downloaded content matches byte-for-byte, and the archive-tier copy (parsing the source container/blob name back out of the active-tier URL, then an authenticated blob-to-blob copy) round-trips correctly. ## Phase 12 — API Startup Resilience (bug found during real local setup)

- [x] **Fixed: the API could not start at all if the database was unreachable.** `Program.cs` called `RecurringJob.AddOrUpdate` (Hangfire snapshot job registration) unguarded at startup; that writes to Hangfire's SQL storage immediately, so a database outage threw straight out of `Main` and killed the process. Found the hard way — during first real local setup against an Azure SQL free tier, where the database auto-pauses on inactivity and the developer's IP rotated (mobile hotspot) out of the SQL firewall allow-list. Both are routine conditions, not exotic ones.
- [x] Registration is now wrapped, logging a loud `LogError` and continuing to start. Verified by booting the API against a deliberately unreachable database: it starts, logs the error, serves requests, and an unauthenticated `GET /api/projects` correctly returns `401` — proving the entire Entra ID authentication path works with no database at all, since JWT bearer validation never touches SQL.
- [x] This also has a practical benefit for setup and testing: the MSAL sign-in flow can be exercised end-to-end without a working database connection, decoupling "is auth wired correctly" from "is the database reachable" — two problems that were previously tangled together and had to be solved in sequence.
- [x] **Gap closed in Phase 13.** This entry previously recorded that recurring jobs stayed unregistered until the app was restarted against a reachable database, with scheduled snapshots silently not running in the meantime. `RecurringJobRegistrationService` removes the need for that restart — see below.

## Phase 13 — Recurring Job Registration Retry

- [x] **`RecurringJobRegistrationService` (an `IHostedService`) replaces the inline try/catch registration in `Program.cs`.** Registering a recurring job is a database write, and doing it once on the startup path meant doing it at the one moment least likely to succeed. Both previous shapes were wrong in different directions: unguarded, an unreachable database killed the process outright (Phase 12); wrapped in try/catch, the API started but the jobs stayed unregistered indefinitely and nothing recovered on its own. The hosted service retries with exponential backoff (5s, doubling, capped at 5 minutes) until the write succeeds, then stops. `AddOrUpdate` is idempotent, so a late registration produces exactly the same three job definitions as a prompt one.
- [x] The cap matters more than the growth rate, and is deliberate: an outage measured in hours must not back off to a retry interval measured in hours too, or recovery is discovered long after it actually happens.
- [x] `await Task.Yield()` before the first attempt. `BackgroundService` runs `ExecuteAsync` synchronously up to its first `await`, on the host's startup path — without the yield, a first attempt against an unreachable database would block the API from serving requests for the length of the SQL connection timeout, which is the exact delay this class exists to avoid.
- [x] Logging is deliberately asymmetric: the first failure carries the full exception, subsequent ones log message-only at `Warning` along with the next retry interval. A database down for an hour would otherwise fill the log with identical stack traces and bury the one that explains what happened.
- [x] Depends on `IRecurringJobManager` rather than Hangfire's static `RecurringJob` facade, which is what makes it testable — the old inline code could not be covered at all. 3 unit tests (`RecurringJobRegistrationServiceTests`): all three jobs register when storage is reachable (asserting on job *ids*, so a copy-paste slip registering the same id three times fails rather than passing on call count); registration succeeds on retry after an initial failure, exercising a real 5-second backoff rather than mocked time; and `StopAsync` returns promptly mid-backoff instead of hanging shutdown until the host's timeout.
- [x] Verified: `dotnet build` clean (0 warnings, 0 errors), 14/14 unit tests pass (11 existing + 3 new).
- [ ] Not covered: the retry path against a genuinely unreachable *SQL Server*, as opposed to a substituted `IRecurringJobManager` that throws. The integration suite has a reachable database by construction, and taking it away mid-run would be testing Hangfire's own connection handling more than this class's behaviour.

## Phase 14 — Snapshots Capture the Register Position

- [x] **`Snapshot` now captures register aggregates, not just project-header figures.** Fifteen new columns covering risk (open count, high-scoring count, total open score), issues (open, severe), programme (total, complete, delayed, worst single slip in days), NEC4 (open early warnings, open compensation events, CE value carried) and SBCC (open variations, variation value, EOT days awarded). Migration `CaptureRegisterAggregatesInSnapshot`, additive with `defaultValue: 0`.
- [x] `CompareSnapshotsQuery` and `SnapshotComparisonDto` extended to match, with a delta for every metric. Every delta is To minus From without exception, **including the ones where "up" is bad** (risk, delay, compensation events) — so a positive number always means the figure increased and never "improved", and a reader never has to remember which way round a particular field was defined. Interpretation belongs to whatever presents it.
- [x] **Aggregates, not per-item capture — a deliberate boundary.** Copying every risk, milestone and compensation event into every snapshot of every active project, daily, would grow without limit for a level of detail nothing currently asks for, and the per-row history already exists in the temporal tables. Aggregates answer "what moved, and by how much" between two dates, which is the question the comparison engine exists to answer.
- [x] **Every definition lives once, in `SnapshotMetrics`**, as EF-translatable `Expression`s. The failure mode this prevents is "open risk" meaning one thing at capture time and something subtly different in a dashboard tile, a committee report or a Power BI dataset — at which point the numbers disagree and nobody can say which is right, because each definition is buried in a different query.
- [x] Two definitions are deliberately *not* the same and it matters: `IsOpenCompensationEvent` excludes Implemented (it is concluded), while `CarriesCompensationEventValue` includes it (it has been paid for and still counts against the budget). Only a Rejected CE is free. Similarly, milestone delay is judged on dates rather than on `MilestoneStatus`, so a milestone that has slipped but whose status nobody updated is still counted.
- [x] Counts and totals are computed by the database, since the scheduled job snapshots every active project on every run. Milestones are the one deliberate exception: the delay calculation uses `DateOnly.DayNumber`, which EF Core cannot translate, and re-expressing it as a SQL date difference would create the second definition `SnapshotMetrics` exists to prevent. A project's milestone count is small and bounded; the other registers are not, and are not materialised.
- [x] 8 unit tests (`SnapshotRegisterCaptureTests`) against a real `DbContext` (InMemory provider), targeting the definitions rather than the plumbing — the decisions most likely to break silently, since each one still produces a plausible-looking number when wrong. ## Phase 16 — Item-Level Snapshot Comparison

- [x] **`CompareSnapshotItemsQuery`: which risks and milestones changed between two snapshots, not just how many.** The aggregate comparison answers "the open risk count went from 12 to 14"; this answers "these two were raised, this one was closed, and this one's score went from 6 to 20" — the version a committee paper can actually be written from. - [x] **Built on temporal history rather than per-item capture, and the choice matters.** Phase 14 named both options. Per-item capture would have duplicated every register row into every snapshot of every active project, daily. ## Phase 22 — Status Transitions Enforced, Not Merely Offered

- [x] **`StatusTransitions` in the Domain, enforced by all six status commands.** Until now they set whatever status they were handed, so the only thing preventing an agreed loss-and-expense claim reverting to Claimed was the absence of a button. ## Phase 23 — Programme Timeline

- [x] **`MilestoneTimeline`: the programme drawn against its baseline**, with a per-milestone bar, a today line, and a four-figure delay summary above it. Replaces a table that could tell you a milestone was 92 days late but not that the whole back half of the programme had moved together.
- [x] **It is not a Gantt, and the Phase 2 entry that asked for one was loose about the data.** A Gantt draws tasks: each has a start, an end, and therefore a length. `Milestone` models a single date with no duration at all. Drawing task bars would have meant inventing durations nobody entered — more familiar to look at, and less true. Each bar therefore spans baseline → current position and its length *is* the slip; a milestone on programme has no bar, only its marker, because nothing has moved.
- [x] Completed milestones use their actual date, not their forecast — the same rule `SnapshotMetrics.DelayDays` applies server-side. A milestone forecast three months late that in fact completed a fortnight late must not read as three months late.
- [x] The summary reports the **worst single slip**, not a total or a mean. Ten milestones one day late is a different programme from one six months late, and summing or averaging makes those two look alike — which is exactly the distinction a reader needs. Slip on key milestones gets its own figure, since those are the ones a committee is told about.
- [x] Today's line is **omitted rather than clamped** when the programme is entirely in the past. A "today" marker pinned to the edge of a programme that finished last year asserts something false.
- [x] **The arithmetic is extracted into `timeline.ts` and unit-tested — 16 tests.** A chart is the one part of an app that cannot be checked by reading it, and nobody in this session can look at the result either. Pulling offsets, direction and date-precedence out of the rendering makes the part that can be wrong verifiable; the component is left with nothing but drawing. One of those tests covers a daylight-saving boundary, where dividing milliseconds without rounding gives 30.958 days and truncates to 30.
- [x] **Vitest now runs in CI.** It was a dependency from the first commit with no tests ever written; `npm test` was never in the pipeline. It is now, so those 16 tests are a gate rather than something that happens to pass locally. Vitest is scoped to `src/` in `vite.config.ts` — a bare glob also collects the Playwright specs, which fail with a confusing "did not expect test.describe() to be called here".
- [x] **5 Playwright tests render the chart in a real browser** against stubbed milestones. Unit tests cannot establish that Recharts drew anything: a chart with correct data and a broken axis domain renders an empty box and every unit test still passes. These assert the axis ticks, one slip bar per milestone, the headline figure, and the tooltip showing the actual date for a completed milestone.
- [x] Two of those tests initially failed on their own expectations rather than on the product: Recharts emits a rectangle for the transparent spacer bar as well as the visible one (6, not 3), and it wraps a long axis label across two `<tspan>`s so "Practical completion" has no space in the DOM. The visible series is now named `milestone-slip-bar` so the count means something rather than passing whatever the chart drew.
- [x] Verified: 16/16 vitest, 15/15 Playwright, `npm run lint`, `tsc` and `npm run build` clean.
- [ ] **Delay-cause analysis is not done, and needs a modelling decision rather than code.** Nothing on `Milestone` records *why* it slipped. The two honest routes are a delay-reason field, or a link from a milestone to the extension-of-time claims that account for it — the second being far more useful for NEC4/SBCC reporting, since it ties programme slip to the contractual events that caused it, and far more of a schema question. Deriving cause from what exists today would be guessing.
- [ ] **Nobody has looked at this chart.** The Playwright tests verify structure — ticks, bars, tooltip content — not appearance. Whether the bars are legible at twenty milestones, whether the labels crowd, whether the colours read correctly in the dark theme: none of that is established, and a DOM assertion cannot establish it.
- [ ] The chart does not paginate or scroll: a project with fifty milestones gets a very tall card. Row height is used rather than a fixed height, so it stays legible rather than smearing, but it will push the rest of the tab a long way down.

## Phase 24 — The EF Tools Talk to the Real Database

- [x] **`AppDbContextFactory` hardcoded a LocalDB connection string, and that string won.** An `IDesignTimeDbContextFactory` takes priority over the startup project's host builder — EF finds the factory and never builds the host at all. So every `dotnet ef database update` went to LocalDB regardless of `--startup-project`, `ASPNETCORE_ENVIRONMENT` or user secrets, while appearing to honour all three.
- [x] **The failure mode is what makes this worth a phase.** It surfaces as a connection error naming a server nobody configured — on a machine without LocalDB, "Unable to locate a Local Database Runtime installation". That reads as a broken workstation rather than a wiring bug, and sends the reader off installing SQL Server Express before anyone thinks to open the factory. It cost real time in exactly that way before being found.
- [x] The factory's own comment claimed `database update` reads the real connection string "when run with `--startup-project SCPM.Api`". It does not, and never did. A comment asserting behaviour the code does not have is worse than no comment: it actively redirects the search away from the cause.
- [x] **`DesignTimeConnectionString` resolves from configuration instead** — `ConnectionStrings__SqlServer` in the environment, then SCPM.Api's user secrets, then the LocalDB fallback. Environment last so it wins: a pipeline that explicitly passes a connection string should not be overridden by whatever a developer happens to have in their secrets store.
- [x] The fallback stays, because `dotnet ef migrations add` never opens a connection — it only needs a provider to generate SQL Server syntax. Removing it would break migration authoring on any machine without a database configured, to fix a problem that only affects `database update`.
- [x] Blank and whitespace values are treated as absent. Clearing an environment variable by setting it empty is common in pipelines, and passing the blank through reaches `SqlConnection` as an `ArgumentException` about an unsupported keyword — an error that says nothing about what is actually wrong.
- [x] **The CI migrate job now passes the connection string through the environment rather than `--connection`.** This is the substantive half of the change. `--connection` bypasses the resolution entirely, so the old factory sailed through CI on every run while failing every developer who ran the documented command — the job was green precisely because it took a different path. It now takes the same one.
- [x] 7 unit tests, and the resolution was verified end to end by running `dotnet ef database update` both ways against this repo: with the variable set it reaches for the named server via the TCP provider; without it, `LocalDB is not supported on this platform`. The contrast is the evidence — one error message read on its own would not have been.
- [x] README gains a "Which database do the EF tools use?" section documenting the order, the user-secrets command, and why `dotnet ef` ignores `launchSettings.json` in the first place.
- [x] Verified: `dotnet build -warnaserror` clean (0 warnings, 0 errors), 104/104 unit tests.
- [ ] **`sqlcmd` lines in the README still hardcode `(localdb)\mssqllocaldb`.** The views and stage-gate procedure aren't EF-managed, so they aren't covered by this resolution and need the server passed by hand. A comment now points at the new section; the commands themselves are unchanged, since teaching `sqlcmd` to read .NET user secrets is not a thing worth building.
- [ ] Nothing reads SCPM.Api's `appsettings.json`. Its `SqlServer` entry is the same LocalDB placeholder as the fallback, so loading it would change no outcome while requiring this class to guess a relative path into another project — but it does mean a connection string placed in `appsettings.Development.json` is ignored by the tools while working for `dotnet run`.

## Phase 25 — Rebaselining as a Governance Act

- [x] **The problem is not that rebaselining loses history — it is that it destroys a question.** `Milestone` is a temporal table, so overwriting `BaselineDate` leaves the old value recoverable through the Phase 15–19 `TemporalAsOf` queries. This phase was originally proposed on the grounds that a rebaseline "silently erases the slip history"; that was wrong, and checking it is what produced the sharper reason below.
- [x] **What actually breaks is reporting.** `Milestone.DelayDays` measures against whatever `BaselineDate` currently holds, so the moment a programme is rebaselined every milestone reports zero slip and the timeline turns green — while the project is exactly as late as it was the day before. "How far are we from the programme sanctioned in March?" stops having an answer, not because anything was deleted but because nothing marks which set of dates was the sanctioned one.
- [x] **`ProgrammeBaseline` + `ProgrammeBaselineEntry`**: a numbered, named, reasoned set of milestone dates, with the approver and approval date recorded separately from whoever typed it in. Slip stops being a property of a milestone and becomes a question about a pair — this milestone, against that baseline.
- [x] **The first rebaseline on an existing project backfills revision 1** from the dates already in place, before overwriting them. Without that step the original programme survives only in the milestone temporal history, where nothing identifies which row was sanctioned: recoverable in principle, useless in practice. No approver is attached to it, because whoever approved those dates did so before this record existed and naming the person running the rebaseline would attribute a decision they did not take.
- [x] **Entries copy the milestone's name rather than joining to it.** A baseline is a record of what was sanctioned, so it must stay readable after the milestone is renamed or soft-deleted. Joining live would silently rewrite a committee-approved document to match today's names, or drop rows entirely once the soft-delete filter applied.
- [x] The new sanctioned date is the actual once a milestone has completed, the forecast otherwise — the same precedence as `DelayDays` and the timeline. Rebaselining a completed milestone to its forecast would enshrine a date events have already disproved.
- [x] **A milestone added after a baseline was sanctioned carries no slip**, and is flagged rather than scored. It is neither early nor late against a programme it was not in, and giving it a number would put an invented figure into the worst-slip headline. Milestones dropped since the baseline are reported **by name, not counted** — one quietly disappearing from an approved programme is something a reader has to see.
- [x] **A filtered unique index enforces one current baseline per project** (`[IsCurrent] = 1 AND [IsDeleted] = 0`). The command maintains that invariant, but a command is one write path and nothing stops a second being added later; two rows both claiming current makes every slip figure depend on which one a query returns first — a wrong number that looks entirely plausible. The `IsDeleted` clause is needed because a soft-deleted row still holds `IsCurrent = 1` and would otherwise block its own replacement.
- [x] `POST /baselines` requires **`CanApprove`, not `CanWrite`**. Changing the measure a project is judged against is a governance act, not an edit.
- [x] 12 unit tests, plus 4 integration tests against real SQL Server for the constraints. The latter cannot be unit-tested: the EF Core InMemory provider does not enforce unique indexes and ignores index filters entirely, so a unit test asserting two current baselines are rejected would pass against a database that accepted them — worse than no test.
- [x] Verified: `dotnet build -warnaserror` clean (0 warnings, 0 errors), 116/116 unit tests.
- [ ] **No UI.** The model needs reviewing before anything is drawn on top of it, and the endpoints are not exercised by any front-end code yet. The timeline still measures against the current baseline only — the comparison endpoint exists but nothing calls it.
- [ ] **Rebaselining moves every milestone.** There is no partial rebaseline, where some dates are re-sanctioned and others held. Real programmes sometimes do exactly that, and supporting it means deciding what a baseline entry means for a milestone that was deliberately excluded — a modelling question, not an oversight.
- [ ] **Nothing links a rebaseline to the contractual events that justified it.** The `Reason` field is free text. Tying it to the extension-of-time claims or compensation events that account for the movement is the same modelling decision Phase 23 flagged for delay-cause analysis, and the two should be settled together rather than separately.
- [ ] The revision number is computed by reading the highest existing one, so two concurrent rebaselines can select the same value. The unique index turns that into a failed write rather than a corrupt record, but the loser gets a constraint violation rather than a retry.

## Phase 26 — Measuring Against a Chosen Baseline

- [x] **A selector on the Programme tab picks which sanctioned programme the timeline measures against.** Phase 25 built the record and the comparison endpoint, but nothing called it — the chart still measured against the live baseline only, which is precisely the reading a rebaseline makes misleading. The feature was there; the question it answers was not askable.
- [x] The contrast is the point, and the browser tests assert it directly: on a rebaselined project the live programme shows **nothing has slipped**, while the superseded revision shows **92 days adrift**. Both figures are true; which one a reader is shown is what a committee cares about.
- [x] **`comparisonToMilestones` adapts the comparison into the shape the chart already takes**, rather than teaching the chart a second data source. Two drawing paths would eventually disagree about what a bar means, and the disagreement would look like a rendering quirk rather than a wrong number.
- [x] **Milestones added since the baseline are dropped from the chart and named beneath it.** They have no sanctioned date, so substituting the current one gives a zero-length bar indistinguishable from a milestone bang on programme — asserting "on time" about something that was never in the programme being examined. Removed ones are named too: appearing or vanishing is not slip and cannot honestly be drawn as a bar.
- [x] **The chart is labelled with the names the milestones carried when sanctioned**, not today's. A chart of the March programme labelled with today's names is a chart of neither. The worst-slip headline follows the same rule, so the tile and the bar under it agree.
- [x] The reason the baseline was replaced is shown alongside the comparison. A reader looking at 92 days of slip against a superseded programme needs what was said at the time, not a separate register to go and find it in.
- [x] The selector is **hidden entirely** on a project never rebaselined: an empty dropdown presents a control that cannot do anything as one that has not been used. The live programme stays on screen while a comparison is loading, rather than the chart blanking — swapping to an empty chart and back reads as data having gone missing.
- [x] `Figure` tiles gained `role="group"` with an accessible label. Genuine accessibility fix: a screen reader previously read "Worst slip", "92d", "Start on site" as three unrelated fragments. It also made the tiles addressable, which mattered because two of them legitimately show the same number when the worst slip is on a key milestone.
- [x] 11 new unit tests and 8 new Playwright tests. Verified: **27/27 vitest, 23/23 Playwright**, `npm run lint`, `tsc` and `npm run build` clean.
- [x] Two Playwright failures were test-expectation errors rather than product bugs, and both were instructive: the worst-slip note correctly reads the *sanctioned* name, and `getByText` resolves to the innermost matching element — the bold lead-in `<span>`, not the paragraph holding the names.
- [ ] **Nobody has looked at this screen.** Same limitation as Phase 23: the tests establish that selecting a baseline changes what is drawn, not that the result is legible. Whether the scope-change note crowds the chart on a project with many added milestones is unknown.
- [ ] **There is no UI for creating a baseline.** `POST /baselines` exists and requires `CanApprove`, but the only way to rebaseline a programme is to call the endpoint directly. The selector can therefore only ever show baselines that arrived some other way.
- [ ] The milestone table below the chart always shows live dates and live slip, even while the chart is measured against a superseded baseline. Defensible — it is the register, not the comparison — but two different slip figures on one screen is a thing a reader can misread.
- [ ] Baselines are fetched on every visit to the tab and are not prefetched with the milestones. One extra request on a screen that already makes several; worth batching if the tab ever feels slow, not before.

## Phase 27 — Rebaselining From the UI

- [x] **`RebaselineForm` on the Programme tab.** Phase 26 could show any sanctioned programme but not create one: `POST /baselines` existed and the only way to reach it was to call the endpoint directly, so the selector could only ever list baselines that arrived some other way.
- [x] **The approver is now taken from the caller's identity rather than the request body — an API change to Phase 26, made because that field could not be used.** `ApprovedBy` is an SCPM user id (the `scpm_user_id` claim minted by `EntraClaimsTransformation`) and a browser has no way to know one; MSAL knows only the Entra object id. The field could therefore only be filled by typing a GUID, which in a record whose purpose is evidencing who sanctioned a change is worse than leaving it empty: **an unusable field invites a wrong one.** What is recorded now is who exercised the authority to make the change — a fact the server holds and can vouch for.
- [x] The paired approver/date validation rules went with it. The handler now sets both or neither, so the pairing cannot be broken from outside, and a validation rule guarding an invariant the type system already holds is a rule that will one day be wrong without anyone noticing.
- [x] **The form is deliberately two-stage.** Everything else on the tab is an edit; this is not. Rebaselining moves the measure the project is judged against, and its most visible effect is that the slip everyone has been watching drops to zero. Correct — and exactly the kind of change that should not happen to someone who had not realised it would.
- [x] **The confirmation names the number that is about to change meaning**: "the worst slip of 92 days (Start on site) will read as zero against the new programme. It stays measurable against this one." A count of affected milestones alone would not tell a reader what they were actually about to do.
- [x] Editing any field after reviewing takes the confirmation away. It states figures for a specific set of inputs, and leaving it up would let someone confirm a summary that no longer describes what they are submitting.
- [x] **The form is not hidden from users without `CanApprove`.** No screen in this app gates on role client-side: the token's roles are a claim about what the server will allow, not the decision itself, and a UI that guesses wrong either hides something permitted or offers something that will be refused. The 403 is reported when it comes, naming approval rights specifically rather than "the request failed".
- [x] When an approval date is entered, the form says plainly that the record will name the signed-in user. Someone entering a committee's date should know that is what it will say before they enter it.
- [x] Client-side validation mirrors `RebaselineProgrammeCommandValidator`, the same convention `NewProjectForm` follows — including the ten-character floor on the reason, which does not make an explanation good but does stop the reflexive "update".
- [x] The mutation invalidates milestones as well as baselines: rebaselining rewrites every milestone's baseline date, and a stale cache would leave the table below the chart showing slip against a programme that had just been superseded.
- [x] 8 new unit tests and 8 new Playwright tests. Verified: **118/118 .NET, 35/35 vitest, 31/31 Playwright**, `dotnet build -warnaserror`, `npm run lint`, `tsc` and `npm run build` all clean.
- [ ] **Attributing a rebaseline to a body rather than a person is not modelled.** A committee takes the decision; an officer records the minute. The record currently names the officer, which is true but not the whole truth. Fixing it properly means deciding what an approver *is* — a user, a committee, or a reference to a decision-register entry — and the last of those is probably right, since `DecisionRegisterEntry` already exists.
- [ ] **Nobody has looked at this form.** Structure and behaviour are verified; appearance is not. Whether the confirmation panel reads as urgent enough for what it does is a judgement no DOM assertion makes.
- [ ] **There is no partial rebaseline**, and the confirmation says so only implicitly by reporting how many milestones move. A user wanting to hold one date while re-sanctioning the rest has no way to say so, and nothing tells them that.
- [ ] A rebaseline cannot be undone from the UI. The superseded revision is retained and the milestone temporal history holds the old dates, so the information is not lost — but reversing one means a further rebaseline, which is arguably the correct governance answer and definitely the unhelpful one at 5pm.

Each phase is designed to be independently shippable and reviewable. Modules from Phase 2 onward follow the same Domain → Application → Infrastructure → Api → Web pattern established in Phase 1.
